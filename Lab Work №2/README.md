# Лабораторная работа №2

## Тема

Использование нотации C4 model для проектирования архитектуры программной системы.

## Цель работы

Получить практический опыт использования C4 model для фиксации архитектурных решений на уровнях системного контекста, контейнеров и компонентов.

## Вариант

**Вариант №8 - система приёма и переработки электроники для крупного магазина электроники.**

Система предназначена для приёма небольшого личного электронного оборудования от клиентов через веб-сайт или киоск, выполнения предварительной оценки, последующей инспекции устройства, корректировки предложения при необходимости, выплаты клиенту и передачи устройства на переработку или перепродажу.

## Краткое описание предметной области

Клиенты сдают бывшее в употреблении электронное оборудование и получают предварительную оценку. После фактического приёма устройство проходит инспекцию. По результатам проверки система либо подтверждает/корректирует предложение клиенту, либо передаёт устройство на дальнейшую переработку или перепродажу. Система должна поддерживать часто меняющийся перечень типов устройств и отдельные правила оценки для каждого типа.

## Выбранный архитектурный подход

Для уровня контейнеров выбрана **сервисно-ориентированная модульная архитектура** с выделением отдельных контейнеров по бизнес-функциям. Такой подход позволяет:

- изолировать процессы каталога, оценки, инспекции и интеграций;
- упростить сопровождение правил оценки;
- развивать отдельные части системы независимо;
- обеспечить понятную структуру сетевого взаимодействия между контейнерами.

## Состав диаграмм

В работе построены следующие диаграммы:

1. **Диаграмма системного контекста** - показывает систему как единое целое, её пользователей и внешние системы.
2. **Диаграмма контейнеров** - показывает внутреннюю структуру системы на уровне приложений и хранилищ данных.
3. **Диаграмма компонентов контейнера "Сервис оценки устройств"** - раскрывает внутреннюю декомпозицию расчёта предварительной оценки.
4. **Диаграмма компонентов контейнера "Сервис инспекции и предложений"** - раскрывает внутреннюю декомпозицию обработки инспекции и итогового решения.

## Диаграмма системного контекста

Диаграмма системного контекста отражает взаимодействие системы с основными ролями и внешними системами.

### Участники и внешние системы

- **Клиент** - сдаёт устройство и получает предварительную оценку через веб-сайт или киоск.
- **Инспектор** - вводит данные о фактическом состоянии устройства и корректирует оценку.
- **Администратор системы** - поддерживает список типов устройств и правила оценки.
- **Руководство** - просматривает отчёты и аналитические данные.
- **Платёжный сервис** - перечисляет деньги клиентам.
- **Партнёр по переработке** - принимает устройства для утилизации.
- **Партнёр по продаже** - получает сведения о пригодных для перепродажи устройствах.

### Технологии взаимодействия

- Пользовательские роли работают с системой через **Web / HTTPS**.
- Интеграции с внешними системами реализуются через **REST API / HTTPS**.

## Диаграмма контейнеров

На диаграмме контейнеров система представлена как набор связанных приложений и хранилища данных.

### Контейнеры внутри системы

- **API Gateway** `[Container: Application]` - маршрутизирует запросы между клиентами и внутренними сервисами.
- **Сервис каталога** `[Container: Service]` - хранит типы устройств и справочные данные.
- **Сервис оценки устройств** `[Container: Service]` - рассчитывает предварительную стоимость устройства.
- **Сервис инспекции и предложений** `[Container: Service]` - обрабатывает результаты проверки и итоговое решение.
- **Database** `[Container: Database]` - хранит справочники, оценки и результаты инспекции.

### Внешние контейнеры и системы

- **Веб-клиент** `[Container: Web Application]` - оформление заявок и просмотр статусов.
- **Киоск** `[Container: Kiosk Application]` - ввод данных об устройстве и получение оценки.
- **Система менеджмента** `[Software System]` - управление справочниками и отчётностью.
- **Платёжный сервис** `[Software System]` - выполнение выплат клиентам.
- **Партнёр по переработке/перепродаже** `[Software System]` - приём устройств на дальнейшую обработку.

### Основные связи

- Веб-клиент и киоск взаимодействуют с **API Gateway** по **HTTPS/JSON**.
- **API Gateway** обращается к сервисам каталога, оценки и инспекции по **REST**.
- Сервисы каталога, оценки и инспекции взаимодействуют с **Database** по **SQL**.
- **Сервис инспекции и предложений** взаимодействует с платёжным сервисом и партнёром по переработке/перепродаже по **REST API**.
- **Система менеджмента** обращается к системе по **HTTPS**.

## Диаграмма компонентов: Сервис оценки устройств

Контейнер **"Сервис оценки устройств"** декомпозирован на компоненты:

- **Контроллер API** `[Component: Controller]` - принимает запросы на оценку.
- **Менеджер правил оценки** `[Component: Service]` - выбирает и координирует правила оценки.
- **Алгоритм расчёта стоимости** `[Component: Service]` - вычисляет итоговую стоимость.
- **Хранилище правил** `[Component: Repository]` - хранит правила и параметры оценки.
- **Движок правил** `[Component: Rule Engine]` - исполняет правила проверки.
- **Кэш оценок** `[Component: Cache]` - хранит результаты недавних расчётов.

### Взаимодействия компонентов

- Контроллер API передаёт запрос на оценку менеджеру правил.
- Менеджер правил читает правила из хранилища правил.
- Менеджер правил передаёт правила на выполнение в движок правил.
- Движок правил передаёт коэффициенты и результаты проверки алгоритму расчёта.
- Алгоритм расчёта сохраняет результат расчёта в кэш.

## Диаграмма компонентов: Сервис инспекции и предложений

Контейнер **"Сервис инспекции и предложений"** декомпозирован на компоненты:

- **Контроллер API** `[Component: Controller]` - принимает данные устройства.
- **Модуль инспекции** `[Component: Service]` - проверяет состояние устройства.
- **Менеджер предложений** `[Component: Service]` - формирует итоговое решение.
- **Хранилище результатов инспекции** `[Component: Repository]` - хранит результаты проверки.
- **Сервис платежей** `[Component: Integration]` - инициирует выплату клиенту.
- **Сервис передачи партнёру** `[Component: Integration]` - передаёт устройство партнёру.

### Взаимодействия компонентов

- Контроллер API передаёт устройство на проверку модулю инспекции.
- Модуль инспекции передаёт результаты инспекции менеджеру предложений.
- Модуль инспекции сохраняет результаты проверки в хранилище.
- Менеджер предложений инициирует выплату клиенту через сервис платежей.
- Менеджер предложений передаёт устройство на обработку через сервис передачи партнёру.

## Вывод

В ходе лабораторной работы была спроектирована архитектура системы приёма и переработки электроники с использованием нотации C4 model. Построенные диаграммы позволили последовательно описать:

- окружение системы и её внешние взаимодействия;
- структуру системы на уровне контейнеров;

Использование C4 model позволило сделать архитектурные решения наглядными, логически связанными и пригодными для дальнейшего проектирования и разработки.
